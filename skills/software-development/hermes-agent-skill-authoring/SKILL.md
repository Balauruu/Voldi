# Authoring Hermes-Agent Skills

## Overview

There are two places a SKILL.md can live:

1. **User-local:** `~/.hermes/skills/<maybe-category>/<name>/SKILL.md` — personal, not shared. Created via `skill_manage(action='create')`.
2. **In-repo:** `skills/<category>/<name>/SKILL.md` or `optional-skills/<category>/<name>/SKILL.md` inside the hermes-agent repo — committed, shipped with the package. Use `write_file` for creation; repository contribution actions require their corresponding authorization. `skill_manage(action='create')` does NOT target this tree.

Apply the procedure, input/output, example, and result-quality standards below to both locations. Apply tier selection, in-repo dependency checks, repository tests, docs regeneration, commits, and PR steps only to an authorized in-repo contribution; a user-local revision is not permission to modify Hermes source or publish it.

In-repo skills must meet the repo's **hardline authoring standards** (see AGENTS.md, "Skill authoring standards (HARDLINE)" — that section is the source of truth; this skill is the operational walkthrough). Reviewers reject PRs that violate them, so meeting them up front is cheaper than a salvage pass later.

## When to Use

- User asks you to add a skill "in this branch / repo / commit"
- You're committing a reusable workflow that should ship with hermes-agent
- You're editing an existing skill under `skills/` or `optional-skills/` (use `patch` for small edits, `write_file` for rewrites; `skill_manage` still works for patch on in-repo skills, but not for `create`)
- Improve installed user-local skills or draft portable candidates using the same writing standards, with the location-specific write boundary below.
- Don't use to implement the task a generated skill describes unless that execution is separately requested.

## Proposal-Only Requests

When the user asks for a proposed revision rather than installation, apply the frontmatter and writing standards to a candidate in the declared project workspace. Leave installed skills and profile configuration unchanged. Bundle required templates with relative pointers so the candidate is self-contained; do not turn a machine-local inspiration file into a runtime dependency. Validate packaging and inspect the procedure, templates and examples semantically. Run representative consumer exercises only within the authorized execution scope: permission to author a skill does not authorize processing a corpus, generating kits or scripts, running calibration, or installing its dependencies. When execution is excluded, report static checks and unexercised behavior separately. Repo commits, docs regeneration, publication, and live activation apply only when separately requested in their corresponding scope.

For this user's skill/framework redesigns, make the actual skill the first review object, not an output generated by it. Once candidate authoring is authorized, read the primary exemplar and necessary supports, construct a complete first `SKILL.md` with its required templates, and expose it before completing the broader research integration. Label its limited source coverage and pending review; early delivery does not waive the remaining requested skills, architecture, detailed plan or source comparison. Do not substitute another analysis dossier or generated-output exercise for inspecting the instructions themselves.

## Revise existing skills in scope

1. **Bind the target.** Resolve the installed canonical name, actual source directory, effective invocation eligibility, and authorized destination. Verify invocation controls against current official documentation, their actual runtime consumers, and the native eligible index; a parsed frontmatter key or another client's policy file is not evidence of enforcement. When an owner requests an eligibility change, distinguish metadata cleanup from an observed runtime transition, and index eligibility from guaranteed model selection. Remove unsupported entries only within the authorized scope rather than inventing an enable flag. Preserve identifiers and effective eligibility otherwise. Read the whole main file and its relevant supports before revision; a spelling variant in the request is not a rename instruction.
   **Done when:** source, edit scope, delivery mode, and installation/publication authority are known.
2. **Map the retained contract.** Account for each material responsibility, owner preference, input, output, conditional gate, and stopping boundary. Improve the procedure without importing one project's layout, paired-review pipeline, or helper machinery as universal prerequisites. Keep standing rules in SKILL.md and only branch-specific depth in a small topical reference set.
   For source-derived redesigns, read the actual source skill/instructions, called templates, schemas, examples and consumer before adapting them; earlier inspections supply navigation, not replacement evidence. Preserve useful native operations, ordering, field groupings, intermediate outputs, change operations and stopping conditions. Adapt only for an explicit target need and show the necessary changes or omissions beside the corresponding original blocks. Keep genuinely different approaches as usable modules or alternative modes rather than average them or force every source into one procedure-heading format. Use `grounded-citations`, **Repository mechanism inspections**, and its `references/repository-mechanisms.md` for detailed source comparison and rights checks. When the owner reopens an architecture or output interface, propose the replacement explicitly instead of treating the rejected shape as a retained constraint.
   Preserve each gate's applicability in templates, examples, summaries and final checklists, not only the detailed procedure; abbreviated instructions can otherwise recreate a prerequisite the main text correctly excludes. Distinguish new creation from authorized maintenance and new work selection from retained-work continuation where those branches differ. Do not make optional descriptive fields block an otherwise settled action. Apply owner-supplied schemas or artifact-only returns to every corresponding output—intermediate proposal, persisted artifact and final return—not just the closing report. Qualify default headings, numbering and file formats accordingly while retaining required semantics and approval/write boundaries; otherwise a late report exception leaves earlier templates contradictory.
   **Done when:** every material requirement has a retained action, output element, constraint, or an explicitly authorized replacement, with consistent branch conditions across all consuming instructions.
3. **Draft through the correct write path.** Use `skill_manage` for authorized installed user-local changes. Use `write_file` or `patch` for staged candidates so the skill manager cannot accidentally change the installed source. For delegated revisions, give each author one exclusive candidate directory, the original inputs, preserved boundaries, and complete-output requirements; keep installation with the coordinator. Reuse known contributor attribution and inspect applicable source terms rather than inventing a handle or grant.
   Preserve existing support-file interfaces, including legacy root-level formats and license notices. If the selected manager cannot address a legacy target, use an authorized file-edit tool for that exact target; do not modify Hermes internals or silently relocate resources to fit the manager, because incoming consumers may depend on those paths. Retain applicable notices in the delivered package, not merely in the drafting workspace.
   **Done when:** complete candidate resources exist in the permitted home, with portable supports, retained interfaces/notices, and concrete inline templates/examples.
4. **Inspect and exercise the actual resources.** Check the requirement map, templates, examples, and companion interfaces. Read a required companion before treating its name as a compatible dependency; a technique import can also bring conflicting approval, deletion, output or execution defaults. State the intended imported behavior and governing task controls at the calling step without weakening explicit owner requirements.
   When behavioral exercises are authorized, use representative inputs and a missing-input or conflicting-control case derived from the declared prerequisites. When a revision changes applicability, exercise the affected branch rather than only its happy path: for example, maintenance without new-record qualification, retained work without a new claim, or an exclusive output schema without an appended default report. If execution is excluded, inspect those branch conditions and examples statically without inventing an exercised result or making unauthorized testing a completion gate. Give independent consumers only their declared inputs and resources; inspect their complete returned output. Separate blind consumer exercises from reviewer-directed regressions: a reviewer who has read baselines/findings can verify a repair, but resetting cases in that same context does not establish fresh-consumer behavior or isolate the skill's effect. For runnable documentation recipes, extract and test the actual final embedded code or its relevant AST statements rather than a separately copied replacement; duplicated test logic can pass while the shipped recipe stays wrong. After corrections, rerun affected behavior or explicitly label the final change inspected but not behaviorally retested. Fixture success establishes only its exercised boundary, not production or cross-platform compliance.
   **Done when:** packaging, semantic review, exercised behavior, and remaining acceptance limits are distinguished.
5. **Integrate and deliver the current revision.** Before replacing an installed target, reread it and reconcile concurrent changes instead of overwriting from an old snapshot. When changing scope, headings, or support locations, inspect incoming pointers in the affected skill interfaces as well as outgoing links; a valid target file can still be reached through an obsolete section name. Repair authorized affected pointers or report an out-of-scope dependency. Assemble every required support before final packaging checks; inspect advisory warnings against actual path ownership, because an intermediate missing asset or a sibling skill's reference is not necessarily a final package defect. Verify the complete installed resources through the native loader when available and compare them with the reviewed revision; a staged candidate or successful main-file write does not establish that the assembled package is usable. Deliver the complete skill and required supports, distinguish staged from installed, and perform repository/publication steps only in their authorized scope. Label superseded authoring/review snapshots historical and point to current checks; recompute final sizes, counts and manifests from the delivered resources instead of transferring earlier measurements, because example or recipe repairs change the verification target.
   **Done when:** the intended reader can reach the current complete resources, the assembled installation is checked rather than inferred, and unresolved dependencies remain visible.

## Decide the Tier First: Bundled vs Optional (in-repo only)

- **Bundled (`skills/<category>/`)** — daily-driver behavior, broadly useful across many user types, low footprint. Hard bar: you can say "a user will load this in 5+ sessions per month" with a straight face.
- **Optional (`optional-skills/<category>/`)** — niche, vertical-specific (blockchain, gaming, finance, one app), recurring-job/task skills, or anything heavy. Installed via `hermes skills install official/<category>/<skill>`.

**When in doubt, optional.** Promoting later is easy; demoting is churn. "Would be useful to anyone who ever needs this" is an optional-tier argument, not a bundled one.

Pick the category by what the tool IS, not what it feels like (an AI-agent CLI goes in `autonomous-ai-agents/` even if it "feels productivity"). Confirm existing categories with `search_files(pattern='*', target='files', path='skills')` and don't invent new top-level categories casually.

**No router / index / hub skills.** A skill whose core content is a routing table pointing at sibling skills adds an indirection hop and duplicates the siblings' own `When to Use` triggers. If the skill would be empty without "load skill X instead" pointers, don't write it — the catalog and each sibling's triggers already do that job.

## Required Frontmatter

Validator source of truth: `tools/skill_manager_tool.py::_validate_frontmatter`. Validator hard requirements:

- Starts with `---` as the first bytes (no leading blank line).
- Closes with `\n---\n` before the body.
- Parses as a YAML mapping.
- `name` field present.
- `description` field present (validator ceiling 1024 chars — but see the repo hardline below, which is much stricter).
- Non-empty body after the closing `---`.

Repo-standard shape (all fields expected, even where the validator doesn't enforce them):

```yaml
---
name: my-skill-name               # lowercase, hyphens, ≤64 chars (MAX_NAME_LENGTH)
description: Concise capability statement, under sixty chars.
version: 0.1.0                    # semver; new skills start at 0.1.0
author: Real Name (github-handle), Hermes Agent
license: MIT
platforms: [linux, macos, windows]   # audit, don't guess — see Platform Gating
metadata:
  hermes:
    tags: [Short, Descriptive, Tags]
    related_skills: [other-in-repo-skill]
---
```

### `description` rules (HARDLINE — the validator's 1024 is NOT the standard)

- **≤ 60 characters.** One sentence. Ends with a period.
- State the capability, not the implementation, and don't repeat the skill name.
- No marketing words ("powerful", "comprehensive", "seamless", "advanced").
- The system prompt skill index truncates at 57 chars + "..." — the trigger/capability must be self-contained in that window.
- If the description contains a `:`, wrap it in double quotes or YAML parses it as a mapping and the docs generator crashes. Quotes don't count toward the 60.

Good: `Track named companies for material news with cited digests.`
Bad: `Use when a user asks to monitor named competitors or companies for product launches, pricing changes, funding, ...` (240 chars — rejected in review)

### `author` rules

- Credit the **human first**, then "Hermes Agent" as secondary collaborator: `Ben Barclay (benbarclay), Hermes Agent`.
- Never `author: Hermes Agent` alone for contributed skills — credit the human, not the tool, even (especially) when an agent drafted the text.
- Maintainer-authored skills: `Teknium (teknium1), Hermes Agent`.

### `related_skills` rules

- Every entry must resolve to an existing **in-repo** skill in the same tree state as your PR. Do not reference skills that were only planned, live in another PR, or exist only in `~/.hermes/skills/`.
- Verify each entry: `search_files(pattern='<name>', target='files', path='skills')` (and `optional-skills/`).

## Platform Gating: audit, don't trust

`platforms:` gates loading by host OS. Set it from what the skill's prose and scripts actually invoke:

| Skill uses only… | `platforms:` |
|---|---|
| Hermes tools + stdlib Python + cross-platform CLIs | `[linux, macos, windows]` |
| bash pipelines, `grep`/`awk`/`sed` chains, heredocs | `[linux, macos]` |
| `osascript`, `defaults`, `pmset` | `[macos]` |
| `apt`/`systemctl`/`/proc` | `[linux]` |

<!-- no-tmp: ok — names the anti-pattern skill authors must avoid -->
POSIX-only signals to search for in `scripts/`: `fcntl`, `termios`, `pty`, `os.fork`, `os.killpg`, `signal.SIGKILL`, `os.kill(pid, 0)` liveness checks, hardcoded `/tmp` `/proc` `/etc`. Default posture: fix cross-platform first (`tempfile.gettempdir()`, `pathlib.Path`, `psutil.pid_exists`); gate narrower only when the dependency is genuinely platform-bound, and say why in `## Pitfalls`.

## Size Limits

- Full SKILL.md: ≤ 100,000 chars enforced (`MAX_SKILL_CONTENT_CHARS`), but target **~100 lines for a simple skill, ~200 for a complex one**. Peer skills sit at 8-14k chars.
- Bulky or branch-specific material goes in `references/*.md`, `templates/`, or `scripts/` — pointed to from SKILL.md, not inlined.
- Don't expect the model to inline-write parsers or non-trivial logic every call — ship a helper script in `scripts/` and reference it by path.

## Convert User Instructions into a Procedure and Deliverables

Before drafting SKILL.md, determine what the skill must consume, do, and produce. Use the supplied request, examples, and corrections; ask only for missing information that materially changes the task.

### 1. Extract the responsibilities

Read the user's instructions and identify:
- The task the skill should perform.
- The inputs needed to perform it.
- Each promised result.
- Constraints on how the task is performed or the result is expressed.
- Conditions that change the procedure or output.

Rewrite vague instructions as observable actions. For example:
- "Include next actions" → Extract each action, its owner, and its deadline; identify missing values instead of inventing them.
- "Make recommendations" → State the proposed action and the supplied evidence or reasoning supporting it.
- "Handle incomplete input" → Specify which missing inputs block the task and which can remain explicitly unknown in the output.

Distinguish requirements from suggestions and inferred design choices. Do not promote an example's incidental details into universal rules.

**Done when:** Every material instruction is accounted for by an action, an output element, or a constraint on those actions and outputs.

### 2. Specify the inputs and missing-input behavior

Write the generated skill's input requirements explicitly:
- What the user supplies.
- Which inputs are required to begin.
- Which inputs are optional and what they change.
- What the agent does when an input is missing.

Name the actual inputs, not generic labels such as "relevant context."

For missing information, choose the applicable behavior:
- Ask when the answer is necessary to perform the task.
- Mark the value unknown when the task can still produce a useful result.
- Omit a conditional section when its triggering condition is absent.

**Done when:** A future agent can determine whether to proceed, ask, omit a section, or report an unknown without guessing.

### 3. Construct each promised output

For each document-producing result, write:

"Create [the actual deliverable name] with these sections:"

Follow it with the actual Markdown template in a fenced code block.

Derive section names and fields from the task. For every section:
- State what content belongs there.
- Specify a useful form: sentence, bullets, table, or repeated record.
- State when the section is included if it is conditional.
- Specify missing-value handling where needed.

Write prompting placeholders:
- Weak: `[Recommendation]`
- Useful: `[State the action to take and the reason it addresses the problem.]`

For tables or repeated records, define the meaning of each field. For machine-consumed outputs, define required keys, types, allowed values, and missing-value rules when validation requires them.

For a simple status or lookup result, specify the return value directly instead of inventing a document.

**Done when:** The output can be produced from the declared inputs without the agent having to invent its structure or interpret empty labels.

### 4. Write the actions that populate the output

Write the generated skill's procedure in execution order. Each significant step must tell the agent:
- Which supplied input or previous result to use.
- What concrete operation to perform.
- What result to retain or write.
- How to recognize completion.

Replace "analyze the material" with the analysis actually needed: extract decisions, compare options, identify contradictions, calculate totals, classify records, or another task-specific operation.

Place the output template beside the step that produces it. Keep this authoring procedure and its teaching example inline.

**Done when:** Every required output element has an identified production step, and every significant step contributes to the requested result.

### 5. Add a complete input/output example

For a document-producing skill, include a short representative input and its complete filled output. Keep both inline.

Use supplied examples when authorized. Otherwise label the example illustrative. Audit the complete filled example against the same task granularity, applicable layers, prerequisites, approval boundaries, factual limits and output contract as the procedure; repair contradictory examples before consumer exercises, because agents imitate examples even when the standing rule says otherwise. Template conformity alone does not establish this consistency.

Show missing or conditional information when it is important to the task. Do not present a partial excerpt as a complete example.

**Done when:** The example demonstrates the expected content, specificity, and missing-information behavior without additional explanation.

### 6. Define checks on the resulting deliverable

Write checks tied to the task:
- Every required result is present.
- Supplied constraints are preserved.
- Required fields contain the right kind of content.
- Missing information is handled as specified.
- Conditional sections appear only when applicable.
- The filled example follows the same rules as the procedure.

A valid SKILL.md is not evidence that these checks pass. When the user requests testing, run a representative task and inspect the actual result. Include a relevant edge case, then revise the instruction or template that caused the failure.

**Done when:** The skill states how to distinguish a usable result from an incomplete, unsupported, or incorrectly structured result.

### Inline teaching example: meeting notes to a decision brief

The following request, input, and output are illustrative. They demonstrate construction of a skill, not an executed meeting or a requirement to include decision briefs in unrelated skills.

**User instructions:** Create a skill that turns meeting notes into a decision brief. Separate recorded decisions from unresolved choices. Include follow-up actions with owners and deadlines. Do not invent missing details.

**Corresponding instructions in the generated skill:**

````markdown
### Produce the Decision Brief

Read the supplied meeting notes.

1. Extract explicitly recorded decisions.
2. Extract choices that remain unresolved; do not resolve them yourself.
3. Extract follow-up actions and any stated owners or deadlines.
4. Write "Not recorded" for missing action owners or deadlines.
5. Populate the following template. Replace its guidance with content.
   If a section has no supported entries, say "None recorded."

Create Decision Brief with these sections:

```md
# Decision Brief

## Recorded decisions
[List only decisions explicitly recorded in the notes.]

## Unresolved choices
[State each open choice and its recorded options.
Do not silently choose an option.]

## Follow-up actions
[Use one row per recorded action. Preserve supplied owners and
deadlines; write "Not recorded" where either is missing.]

| Action | Owner | Deadline |
|---|---|---|
| [Describe the recorded follow-up action] | [Recorded owner] | [Recorded deadline] |
```

Done when: Every recorded decision, unresolved choice, and follow-up
action is represented, and no owner, deadline, or resolution was invented.
````

**Complete illustrative input:**

```text
Use the library room for the reading group.
Alex will check availability.
We still need to choose Friday or Sunday.
```

**Complete illustrative output:**

```markdown
# Decision Brief

## Recorded decisions
- Use the library room for the reading group.

## Unresolved choices
- Choose Friday or Sunday for the reading group.

## Follow-up actions
| Action | Owner | Deadline |
|---|---|---|
| Check library-room availability | Alex | Not recorded |
```

| User responsibility | Concrete implementation |
|---|---|
| Separate decisions from unresolved choices | Two distinct sections and extraction steps |
| Include follow-up actions | One row per action |
| Include owners and deadlines | Explicit columns |
| Do not invent missing details | A defined missing-value marker |
| Produce a useful brief | A complete output that follows the template |

## Body Structure (modern section order)

```
# <Skill> Skill
2-3 sentence intro: what it does, what it doesn't do, dependency stance.

## When to Use          — bulleted triggers (+ "Don't use for:" counter-triggers)
## Prerequisites        — exact env vars, installs, API key sourcing
## Inputs               — named inputs and missing-input behavior
## How to Run           — canonical invocation through the `terminal` tool
## Quick Reference      — flat command list, no narration
## Procedure            — concrete actions and completion criteria;
                          inline output templates beside their production steps
## Example              — representative input and complete output,
                          when the skill produces a document
## Pitfalls             — known limits, things that look broken but aren't
## Verification         — checks on the task result as well as packaging
```

Use this section order as a default, not a universal normalization template. Preserve a source's useful phase/mode construction when adapting it; the required semantics need not have identical headings across skills. When to Use + actionable body + Pitfalls + Verification are the minimum. How to Run and Quick Reference apply only when the skill needs them; a CLI-wrapper or simple lookup need not invent a document or document example. Cut marketing intros, "Setup Check" no-ops, and re-explanations of env vars already in Prerequisites.

### Reference Hermes tools, not raw shell

When the skill needs a capability, name the actual exposed Hermes tool in backticks: for example, `terminal`, `read_file`, `write_file`, `patch`, `search_files`, `web_search`, `web_extract`, `browser_exec`, `vision_analyze`, or `delegate_task`. Check the current tool schema before writing a runnable recipe; do not copy a browser or scheduling tool name from another runtime. For `browser_exec`, follow its supplied helper API and state boundaries rather than assuming a separate navigation tool. Do NOT name shell utilities the agent already has wrapped (`grep` → `search_files`, `cat` → `read_file`, `sed`/`awk` → `patch`, `find`/`ls` → `search_files target='files'`). A CLI-wrapper skill should frame invocations as `terminal(command="{tool} ...", timeout=...)` — bare shell prose ("run `foo --version`") is a review-blocking non-conformance. If the skill depends on an MCP server, name it and document setup in Prerequisites.

### Never use machine-local paths

Write repo-relative paths (`skills/...`, `tools/skill_manager_tool.py`). A `/home/<you>/...` path baked into a committed skill breaks for every other user and is an instant review flag.

## Writing Quality Principles

A skill exists to make the agent's process more predictable — the agent reliably follows the same useful discipline.

1. **Optimize for process predictability.** If a line does not change behavior, cut it.
2. **Choose the right context load.** The description is paid for every turn; details go in the body or linked references.
3. **End steps with completion criteria.** Checkable and, when it matters, exhaustive: "every modified file accounted for" beats "summarize changes."
4. **Co-locate rules with the concept they govern.**
5. **Use strong leading words** ("tight loop," "root cause," "regression test") over long repeated explanations.
6. **Prune duplication and no-ops.** "Be careful" and "use best practices" don't change model behavior — replace with a checkable criterion or delete.

## Tests and Docs (required for repo skills)

1. **Tests** live at `tests/skills/test_<skill>_skill.py` — stdlib + pytest + `unittest.mock` only, no live network. Run via `scripts/run_tests.sh tests/skills/test_<skill>_skill.py -q`. (The generic `tests/tools/test_skill_manager_tool.py` passing proves nothing about YOUR skill.)
2. **Docs regen:** run `python website/scripts/generate-skill-docs.py`, then apply scope discipline — the generator rewrites EVERY auto-gen page. `git checkout --` everything that isn't yours; the final diff must show only your SKILL.md, your one per-skill docs page, a one-line catalog row, and a one-line `website/sidebars.ts` insertion (verify with `search_files(pattern='<your-slug>', path='website/sidebars.ts')` — exactly one hit, or the page is an orphan).
3. **`.env.example`** (only if the skill needs new env vars): one clearly delimited commented block; touch nothing else in the file.

## In-Repo Contribution Workflow

Use this sequence only for an authorized repository contribution; user-local revisions follow **Revise existing skills in scope** above.

1. **Survey peers** in the target category with `search_files(target='files')` and read 2-3 peer SKILL.md files to match tone and structure. Prefer extending an existing skill over creating a narrow sibling.
2. **Decide tier and category** (see above). When in doubt, optional — and ask before pushing rather than defaulting.
3. **Design and draft the skill.** Follow "Convert User Instructions into a Procedure and Deliverables" above. Then use `write_file` to write SKILL.md in the authorized location (`skills/<category>/<name>/SKILL.md` or `optional-skills/...` for an in-repo contribution), applying the frontmatter and body standards. Keep its required output templates and representative input/output example inline.
4. **Validate locally**:
   ```python
   import re, pathlib
   from ruamel.yaml import YAML
   content = pathlib.Path("skills/<category>/<name>/SKILL.md").read_text()
   assert content.startswith("---")
   m = re.search(r'\n---\s*\n', content[3:])
   fm = YAML(typ="safe").load(content[3:m.start()+3])
   assert "name" in fm and "description" in fm
   assert len(fm["description"]) <= 60, f"description {len(fm['description'])} chars — hardline is 60"
   assert fm["description"].endswith(".")
   assert "platforms" in fm
   assert len(content) <= 100_000
   ```
   Also verify every `related_skills` entry exists in-repo.
5. **Add tests + regen docs** (previous section).
6. **Git add + commit** on the active branch; open a PR.
7. **Check loading and discovery separately.** Verify existing revisions with `skill_view` and the actual installed resources; do not infer stale contents from the conversation's cached skill index. Refresh discovery in a new session when necessary, without forcing an application restart merely to verify an existing skill.

## Editing Existing In-Repo Skills

- **Small fix:** `skill_manage(action='patch', ...)` works on in-repo skills, as does `patch`.
- **Major rewrite:** `write_file` the whole SKILL.md.
- **Supporting files:** `write_file` to `references/`, `templates/`, or `scripts/` under the skill dir.
- **Always commit** — in-repo skills are source, not runtime state. Re-run the docs generator when frontmatter changed.

## Common Pitfalls

1. **Using `skill_manage(action='create')` for an in-repo skill.** It writes to `~/.hermes/skills/`, not the repo tree. Use `write_file`.
2. **Trusting the validator's limits as the standard.** The validator allows 1024-char descriptions; review rejects anything over 60. The validator doesn't check `platforms:`, author format, tests, or docs — review does.
3. **`author: Hermes Agent` on a contributed skill.** Credit the human first.
4. **Leading whitespace before `---`.** Validation fails on any leading blank line or BOM.
5. **Description too generic or trigger buried past char 57.**
6. **`related_skills` pointing at skills that don't exist in-repo** (user-local, planned, or in a sibling PR).
7. **Duplicating a peer.** Survey the category first; extend rather than sibling.
8. **Skipping the docs generator or pushing its unrelated drift.** Both directions are wrong: no regen = orphan skill with no docs page; blind regen = a ballooned diff full of other skills' drift.
9. **Confusing discovery with content loading.** Follow the loading/discovery check above; a cached index is not evidence that an existing file revision cannot be loaded.
10. **Letting skills accumulate sediment.** When adding a rule, remove the old wording it replaces.
